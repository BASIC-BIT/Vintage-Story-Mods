# Standalone execution of Vintage Story GUI rendering

Date: 2026-09-08. Research only. Target: produce complete images of existing production dialogs without starting Vintage Story. Sources examined: local decompiled 1.22.6 API/client implementation, current The BASICs dialogs, installed game shaders and primary library documentation. **No standalone dialog has been executed by this investigation.** Version-specific conclusions need checking against the eventual target DLLs.

## Conclusion

A standalone host for the real dialog and control code is a credible engineering direction. The examined settings controls mostly produce Cairo surfaces and then request a small family of texture, clipping and overlay operations. We can retain those original layout, painting and interaction implementations and provide the services normally supplied by the game. This is materially more faithful than recreating settings layouts in HTML or a second GUI framework. Feasibility is supported by source structure; runtime bootstrap and pixel parity remain experiments. The earlier [research note](2026-09-08-production-ui-render-testing.md) recommended a real-client harness first. This note supersedes that sequencing recommendation for the user's explicit no-game preview objective.

The crucial distinction is **reuse the GUI implementation, replace its rendering environment**. Do not fork every control. The software backend would implement a bounded graphics contract under the actual compiled GUI code. Unsupported operations must fail explicitly, so a nice-looking incomplete image cannot silently become a passing test.

## The fidelity traps that deserve explicit tests

**Raw surface format is not enough to identify alpha semantics.** Cairo ARGB32 normally stores native-endian premultiplied channels, with potentially padded row stride. Flush before reading. But the game can call `DemulAlpha` before upload. Capture actual bytes and the blend mode used at each draw; do not automatically unpremultiply or premultiply every texture. Cairo's standard OVER operation is suitable for correctly represented premultiplied composition, but the game also issues standard-alpha draws. Its blend implementation uses ONE/ONE_MINUS_SRC_ALPHA for premultiplied and SRC_ALPHA/ONE_MINUS_SRC_ALPHA for standard. Transparent-target alpha behavior needs validation separately from final RGB over an opaque background. [Cairo image surface documentation](https://www.cairographics.org/manual/cairo-Image-Surfaces.html), [Cairo operators](https://www.cairographics.org/operators/), local blend/composer sources above.

**Filtering and pixel centers matter.** Cairo uploads set linear minification and selectable linear/nearest magnification. Production overloads truncate some coordinates to integers. A generic high-quality image resize may look nicer and still be less faithful. Record original texture dimensions, target dimensions, filter and exact effective coordinates in the command trace. [ClientPlatformWindows:2281](D:/bench/vs/source/vintagestory/1.22.6/decompiled/VintagestoryLib/Vintagestory/Client/NoObf/ClientPlatformWindows.cs:2281), RenderAPIGame overloads above.

**The GUI is still shader-rendered.** Normal texture draws reset several shader flags and apply matrices, but the GUI fragment shader also contains alpha-test discard, tint, overlay and other branches. The installed shader's basic path multiplies sampled texture by color. The host must reproduce the active branch and frame defaults, not assume every shader feature is active or irrelevant. The bounded inspection did not fully establish inherited depth-test/write and shader-uniform defaults at the GUI stage. This is a concrete next research/probe item before claiming complete parity. [ClientMain:1332](D:/bench/vs/source/vintagestory/1.22.6/decompiled/VintagestoryLib/Vintagestory/Client/NoObf/ClientMain.cs:1332), [orthographic setup:1554](D:/bench/vs/source/vintagestory/1.22.6/decompiled/VintagestoryLib/Vintagestory/Client/NoObf/ClientMain.cs:1554), [installed gui.fsh:59](D:/Games/Vintagestory/assets/game/shaders/gui.fsh:59).

## Proposed standalone architecture

This is a design inference from the sources, not an implemented library:

1. A test process loads the mod and compatible game assemblies, Cairo/native dependencies, fonts and assets. Configure viewport, GUI scale, locale and theme deterministically.
2. A strict `ICoreClientAPI` fixture supplies the exercised Gui, Render, Assets, Input, Settings, Logger and elapsed-time services. Implement only intentional harmless environment operations such as recorded sound requests; unknown calls throw. Network callbacks record fixture actions and never contact a server.
3. The Gui adapter builds real composers and reuses production `TextTextureUtil`/icon helpers. Its texture methods copy CPU buffers and manage IDs. The Render adapter records stateful graphics commands and rasterizes them into a framebuffer.
4. Instantiate production dialogs and route synthetic mouse/key events through their actual event handlers. Advance a fixture clock and flush any scheduled recompose work deliberately. Snapshot default, hover, focus/selection, open/scrolling dropdown and edited/status states.
5. Export PNG plus a manifest of assemblies/assets/fonts, inputs, clock, control bounds, used API members, commands and unsupported-operation count. Baseline testing consumes these artifacts after repeatability is established.

A single fixture process per render batch is initially preferable to broad parallelism because `RuntimeEnv.GUIScale`, GUI style, localization and asset/pattern caches are process-global dependencies. Reusing code does not remove the need to isolate that environment. The prior note documents the verified dice surface probe and font-default difference.

## CPU compositing versus standalone software OpenGL

A CPU texture/rectangle backend is attractive for the observed 2D controls because the expensive layout and raster painting already exist in Cairo. Keep the backend contract at the API layer, so another implementation can be added if necessary. A standalone offscreen OpenGL host with Mesa LLVMpipe is another no-game option: LLVMpipe is a software rasterizer, potentially allowing original shader execution instead of manually emulating more graphics semantics. It still requires API bootstrap, textures, matrices and a compatible context; no working Vintage Story harness using it has been demonstrated here. [Mesa LLVMpipe documentation](https://docs.mesa3d.org/drivers/llvmpipe.html).

Prefer the CPU proof for these settings controls. If the exercised scope expands to item meshes, shader effects, rotation or complex depth interactions, compare the cost of extending the CPU backend with an offscreen GL backend. Neither alternative requires opening the game for everyday previews. A game screenshot can be an occasional calibration reference, not the preview runtime.

## Phased proof and acceptance criteria

1. **Bootstrap proof:** execute one complete `LanguageConfigDialog` composition in a standalone test process, no client executable. Capture all texture uploads and an API-use manifest. Pass only with zero unclassified calls and complete expected controls/assets. Stop and inventory any static initializer, concrete client cast or uncaptured native dependency; do not add silent mocks until the exception disappears.
2. **Complete-frame proof:** render default, focused input, hovered button and open dropdown through production dialog/control rendering. Assert expected bounds/state as well as output. Include overlapping menu rows, tooltip at viewport edge, long selected text, text selection and two GUI scales. A static background PNG alone does not meet this step.
3. **Backend conformance:** test alpha modes, texture replacement/deletion, nearest/linear scaling, nested/raw scissor transitions, tint, transform stack and depth/alpha-discard behavior against the inspected equations and small controlled references. Unresolved depth/shader defaults block a fidelity claim, not further research.
4. **Calibration:** compare a bounded set of full dialog states with real-game captures when available. Trace differences to backend semantics, fonts or fixture inputs before widening tolerances. Until then label output as production-code standalone preview, with uncalibrated final composition.
5. **Coverage expansion:** execute all actual admin settings categories and language-dialog states using the same backend; demonstrate an intentional production visual regression changes/fails the image test. Retain current/baseline/diff artifacts and explicit baseline review. Later control families earn support via failing fixtures and conformance tests, not speculative blanket APIs.

The valuable success criterion is a test that calls the real dialog, drives its real state and produces the complete supported UI image without a game process. Perfect emulation of every possible Vintage Story UI is a separate and much larger claim. This research identifies a credible path toward the former while leaving extension points for the latter.
